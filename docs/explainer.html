The XTE Field Guide

Why a four-colour Bluetooth shelf label works the way it does, with the parts you can poke: how the ink moves, why the screen flickers, how the bytes hang together, and how the handshake runs. The normative byte layouts live in docs/protocol.md; this page explains them.

At restPress refresh to watch a four-colour waveform. Time is compressed about 4×.

This is a model of what the real panel does, not a recording. The real PSJ-213 takes about 20 seconds and acknowledges over BLE 60 ms in, long before the ink settles.

1. The tag

The Poshiji PSJ-213 is a 2.13-inch electronic shelf label with a four-ink panel: black, white, red and yellow. It has a Bluetooth Low Energy radio, an NFC tag, two CR2450 cells in parallel, and no documentation. "Poshiji" is the reseller's brand. The firmware, the advertisement and the vendor SDK all call the protocol something else, and that name is stamped in every frame: XTE.

The same firmware ships in a family of sizes. The vendor's manual lists them:

Tags like this are sold as generic "4 colour BLE ESL" on AliExpress and similar for a few dollars, and no listing says XTE. The housing is the visible clue: a white rounded case with a small round LED window at the top right of the bezel, and listing renders showing a red header, a yellow price block and a barcode, which is the vendor's default template. After that, identify one by its advertisement (manufacturer ID 0x5258, data starting X R or X T), by the reseller app name "POSHIJI ESL Management System", or by the NFC record below. Tags advertising service FEF0 are Gicisky, a different protocol.

The tag tells you what it is three ways. Its NFC record reads 36330B001D9F,140,122,250,BWRY,0,0,0,0,CN: the reversed MAC, a type code of 140, the two panel dimensions, and the ink set. Its factory screen prints 2.13 H:2 V:4.0.2. Its advertisement carries the same numbers in binary. Section 5 decodes it.

2. How e-ink refreshes, and why it flickers

This section is inference: general electrophoretic-display physics applied to what the PSJ-213 visibly does during a refresh. No controller datasheet or waveform table for this panel has been read.

An electrophoretic display has no frame buffer on the glass. Each pixel is a microcapsule of clear fluid holding pigment particles, and the picture is wherever the particles physically are. To change a pixel the controller applies a voltage across the capsule and the particles drift. Nothing measures where they end up. The controller runs a scripted sequence of voltage pulses, called a waveform, that is long enough for the particles to reliably arrive.

Four pigments, one field

A monochrome panel is simple: white particles carry one charge, black the other, so one field direction pulls white to the surface and the reverse pulls black. A four-colour panel adds red and yellow pigments with different charge magnitudes and mobilities. There is no voltage that means "yellow". The waveform has to first scramble everything to a known state, then sort the pigments by how fast they respond so the wanted one ends on top.

What you see

  • Fast black-white flashes first. These are clearing inversions. Black and white are the most mobile pigments and respond to short pulses. Rapid reversals shake loose particles stuck from the previous image, which would otherwise leave ghosts.
  • Slower pulses after. The colour-sorting phases hold the field longer per step because the colour pigments have less charge or more drag. Some phases use a lower voltage or a duty-cycle pattern, which reads as a slower pulse.
  • Regions out of step. The waveform lookup is per pixel per frame, keyed on the previous and next colour. Two areas going to the same target from different starts run different branches of the table, so they pulse at different rhythms even on a solid image.
  • Temperature. The fluid thickens when cold. The controller picks a longer waveform from a temperature-indexed table, so the last advertised byte is very likely the sensor reading the firmware uses to select it.

The tag acknowledges the refresh command about 60 ms after receiving it. That means "waveform started", not "image visible". Expect 15 to 25 seconds of visible churn afterwards. This is normal and the vendor's own app looks identical.

3. Panel geometry, and the shear that taught it

You look at the PSJ-213 in landscape, 250 wide by 122 high. The panel controller does not. Its source lines run along the short edge, so the native buffer is 122 columns by 250 rows, portrait. Each row is 122 pixels padded to 124, which at two bits per pixel is 31 bytes. The whole buffer is 7750 bytes.

Send it landscape rows and every row lands 63 bytes on from the last, but the panel reads them 31 bytes at a time. Each displayed line starts one byte later than it should, so vertical edges become diagonals. The slider below reproduces the effect. The two wrong values were the two photos taken during reverse-engineering; the slopes are how the correct stride was solved.

The panel always reads 31-byte rows. Slope in pixels per column equals 4 × (sent − 31), wrapping every 124 pixels.

The recipe

  1. Draw the label in landscape, 250 × 122, using only the four exact colours.
  2. Rotate it 90° counter-clockwise. It is now 122 × 250.
  3. Pack rows of 122 pixels, padded to 124, four pixels per byte.
  4. Buffer row 0 is the right-hand edge as viewed. Byte 0 of each row is the top. No vertical flip.

4. The BLE pipe

The tag exposes one vendor service with two characteristics: a write-without-response pipe in, and a notify pipe out. There is no framing at the GATT level. Whatever you write appears at the firmware as a byte stream, and the firmware finds frame boundaries by the XTE magic and length field.

The UUID base xxxx2760-08C2-11E1-9073-0E8AC72Exxxx is the Arm Cordio BLE stack's proprietary data-transfer sample. It identifies the software stack inside the chip, not the product, which is why searching for it finds Mi Band firmware and not shelf labels.

Two bits per pixel

The packer matches each source pixel exactly against three colours and calls everything else black. That is why anti-aliased edges must be quantised before packing: a pink edge pixel is "anything else", and becomes a black outline. Click the pixels to see the codes and the byte they pack into.

Codes: white 1 · yellow 2 · red 3 · black 0. First pixel in the top two bits.

RLE, the vendor's way

The compression is run-length with a twist: the packed bytes are split into two halves and each half is encoded separately as count, value pairs with count capped at 255. The two encoded halves are concatenated. The tag accepts raw data too, so a first port can skip compression and send 00. Flat labels compress well; a dithered photo does not compress at all and the encoder falls back to raw.

packed   09 09 09 09 | 09 09 01 01
halves   04 09       | 02 09 02 01
result   04 09 02 09 02 01      (plain RLE would say 06 09 02 01, and be wrong)

Normative rules, including greedy run splitting and the equal-length tie: protocol.md §7.3.

8. The handshake

A push is three exchanges. Times are from a real PSJ-213 session over BlueZ.

Nothing in the exchange identifies the host, names a store, or checks a binding. An unprovisioned tag straight out of the box takes the push. Whatever the base station and cloud do, they do it over this same pipe.

9. Lost packets

Transcribed from the vendor application. No observed push has lost a packet, so this path has never been watched on a tag.

Write-without-response has no acknowledgement, so packets can vanish. The tag keeps a bitmap of which indexes arrived. If the refresh command finds gaps it answers 68 instead of FF and attaches the bitmap from byte 8, most significant bit first, one bit per packet, 1 for received.

  1. Expand the bitmap and take the first total bits.
  2. Resend every packet whose bit is 0.
  3. Wait 100 ms and send the refresh again.
  4. Give up after three rounds.

Containers over 204 800 bytes go in batches. Each batch gets its own allocation with an offset, its own packet numbering, and a 02 verify command that returns the same kind of bitmap from byte 7. Only the last batch ends with a refresh. No PSJ-213 image comes anywhere near that size, but it is the path firmware updates take.

11. How it was found

The tag arrived with no app and no base station. Weeks of reconnaissance established the panel size from NFC, decoded the advertisement, mapped the GATT table, identified the Cordio stack from the UUID, found SWD pads on the board and read a Cortex-M0 CPUID through a bit-banged ESP32 probe during the boot window before the firmware locks the port. None of that gave the protocol.

What did was the vendor's operation manual. Its download page carried a QR code, the QR code led to an Android APK on the reseller's own server, and the APK turned out to be a WeChat mini-program in a wrapper. Mini-programs ship as JavaScript, so the whole BLE layer was readable: frame builders, the pixel packer, the send state machine with its patch loop. The SDK inside calls itself chromaink.

The spec in this repository was written from that reading, then checked the other way: a Python codec generates the same bytes the vendor's code does for the same input, byte for byte, and those vectors are the conformance suite every other port must pass. The first push onto real hardware succeeded at the protocol level immediately and came out sheared, which is how section 3 was learned. Three pushes later the image was straight.

The vendor code is not in the repository. Ports are written from the spec alone.
